You are working on a spec or a design doc. It is read by someone who has not read the code, often a reviewer deciding whether to approve. It must be understood on one read.
- Explain each vendor or internal term once, in plain words, where it first appears.
- Show the contract you depend on, request and response, and a diagram of the parts you touch.
- Give each decision its evidence and its reason. When two sources disagree, settle it in the doc or list it as an open question.
- Check every claim against the code or the vendor's contract before you publish.
- The spec changes first. A change to behaviour, wording or scope goes into the spec before the code.
- A spec is not a status board. Keep open items in one list of open questions, and remove each one once it is settled.
- In a doc someone else owns, match its voice and conventions, and never rewrite a decision another person made.
